# ADR 0009: 入站密钥通道——多通道 first-match、透传认证头配置进出两用、出站原位替换

日期: 2026-10-22
状态: accepted（修订 ADR 0008 决策 3）

## 背景

外部客户端请求 aidog 时，分组密钥（= 分组名）原先只认三处、取第一个非空值：`Authorization: Bearer` → `x-api-key` → `?api_key=`。Azure 风格 `api-key`、Gemini 的 `x-goog-api-key` / `?key=`、`Authorization: Key xxx` 等写法定不了组；客户端同时带上游 key 和分组密钥时，取到上游 key 直接 404。用户还要求透传平台能自定义密钥所在的 header。四轮 ask-me 拍板（决策账本 `.scratch/memory/2026-10-22.md`「入站分组密钥多通道解析」节）。

关键约束：解析密钥发生在定组之前，此时不知道请求会落到哪个平台类型。

## 决策

1. **多通道 first-match**：候选按序为——所有透传平台的自定义通道（`auth_header` + `auth_template`，同名头每个模板都试）→ `Authorization`（整值 + 第一个空格后的部分，方案词不限）→ `x-api-key` → `api-key` → `x-goog-api-key` → `?api_key=` → `?key=`。逐个与分组密钥精确比对，第一个对上的胜。对所有代理请求生效（HTTP / WS / 模型列表）；本地 API `/api/group-info`、`/api/notify` 不变。
2. **透传平台认证头配置进出两用**：`auth_header` + `auth_template` 既是出站注入格式，也是一条入站密钥通道。不新增入站字段。
3. **透传出站原位替换**：客户端从哪个通道传来，就在同一通道（保留方案词 / 模板外壳）换成平台 key；平台显式配置过认证头时按配置注入。未用于定组的其它凭证头一律剥。
4. **全部密钥通道转发前剥离、日志脱敏**（含自定义头名与 `?key=`）。

## 理由

1. 每个候选都要精确等于某分组密钥才定组，多候选不会多放行；first-match 解决「客户端自带上游 key」的冲突。
2. 定组前不知道平台类型，「只对透传生效」无法实现；一份配置两头用，用户只需理解一个概念。
3. 透传不识别协议，客户端用的通道格式最可能就是上游要的格式。

## 后果

- 透传平台改 `auth_header` 会同时改变哪些入站请求能定组。
- 任一透传平台声明的自定义头名对所有分组生效（运行时取并集）。
- 某个分组密钥恰好等于客户端发的上游 key 时会被定组——分组密钥是用户自建的，视为可接受。

## 备选方案

- 全局自定义头名列表（运行时语义本就全局）：用户选了挂在平台上，弃。复活条件：非透传分组也需要自定义通道。
- 独立入站字段 `inbound_key_header`：多一组配置，弃。复活条件：出现「客户端用 A 头传组、上游要 B 头」的真实需求。
- 固定方案词表（Bearer / Key / Api-key / Token）：遇新词要改代码，弃。
- 仍取首个非空值：自带上游 key 的客户端 404，弃。
