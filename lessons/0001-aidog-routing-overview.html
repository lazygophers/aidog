aidog 路由全景

第 1 课 · 一张图看懂：请求进来，怎么过滤、怎么排序、怎么换模型。约 10 分钟读完。

「路由」回答一个问题：这个请求发给哪个平台、用什么模型名。答案是三步：先过滤（哪些平台现在不许用），再排序（可用的按什么顺序试），排序规则就是四种「路由模式」。定下顺序后产出一个候选名单，第一个失败就试第二个——这就是重试链。

入口：分组鉴权

客户端（如 Claude Code）连代理时带的密钥就是分组名。路由只在这个分组关联的平台里挑，绝不会越组——整组没平台可发，请求就失败。这就是「请求隔离」。

特例：单平台分组短路。组里只有一个平台（或只启用了一个）时，上面六道关大部分被跳过——哪怕它被自动停用、被熔断，也照样发请求（反正没得选，不试就全死）。只有两个硬停：手动停用、高峰禁用。出处：router/mod.rs:93-113、candidates.rs:201-256
整组被高峰禁用时，请求返回失败并落一条审计日志（拦截方=路由器，原因=高峰）。其他原因导致的整组无候选只记警告、不落库。出处：candidates.rs:164-179

第 3 节 · 四种路由模式 = 四种排顺序的方法

过滤剩下的平台，按分组选的模式排成一个候选名单。名单第一个就是本次请求的首选，失败就顺位往下试。

模式一句人话怎么排
failover
故障转移		平时用主力，坏了用备胎按优先级从高到低，固定顺序
load_balance
负载均衡		按体重抽签，谁都可能当首选按权重加权随机选首选，其余按权重从大到小排在后面
health_aware
健康感知		负载均衡 + 先踢掉病号先被熔断闸门踢掉不健康平台，剩下同 load_balance
sticky
粘性会话		同一个会话尽量粘同一个平台负载均衡选好首选后，若这个会话之前绑过某平台且它还健康，就继续用它

枚举定义：src-tauri/crates/aidog_db/src/models/protocol.rs:291-305 · 各排序实现：router/ordering.rs

四种排序都通用的叠加规则

  1. 有效权重 = 权重 × 组内优先级（1~10 级，乘起来放大差距）。mod.rs:87-91
  2. 包月平台优先：订阅制 coding 套餐平台整体上浮到前面（月包干额度，优先烧它省钱）。ordering.rs:40-42
  3. 快过期先用：快到期的平台在同档位里排前（额度别浪费）。ordering.rs:26-28
  4. 显式模型映射插队：分组里配了「模型 A → 平台 X」的映射时，平台 X 提到名单最前。candidates.rs:150-162

第 4 节 · 熔断器：三态循环

熔断是纯内存机制，界面上的平台状态不动，重启应用即清零。两种失败会触发：限流（429）和连不上（connect 失败）；服务器 5xx、超时掐线不触发。连不上还带本机断网保护：一分钟内一半以上平台都连不上，判是自己网络问题，全部不计。

兜底：熔断踢光也放行。候选全被熔断踢掉时，熔断被绕过、照常透传——宁可把上游真实错误透给客户端，也不整组死锁。只有配额/鉴权冷却造成的空候选不绕。出处：candidates.rs:131-145

第 5 节 · 模型怎么换：三级联 + 槽位

排好顺序后，每个候选平台还要回答第二个问题：发给它时用什么模型名（各平台模型命名不同）。按优先级取第一个命中的：

拿到模型表后再做槽位匹配：请求的模型名里含 opus / sonnet / haiku / gpt 字样，就用表里对应槽位的值；都不匹配用默认值；连默认都没有，原名透传（去掉 [1m] 这类预算后缀）。另外分组里配了显式「模型映射」时，映射目标模型压过这一切，所有候选共用它。model_mapping.rs:8-31

讲给别人的一句话总结：「密钥选组，六道闸门筛平台，五种模式排名单，失败顺位重试；模型按 时段→高峰→默认 三级取，槽位名换真名。」
