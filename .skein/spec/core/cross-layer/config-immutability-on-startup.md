## 触发场景

启动流程（手动 / 自启动）中需要读取用户持久化设置值并用于初始化系统状态时。

## 陷阱

启动失败后或运行中需要调整的状态（如实际绑定端口、实际运行参数）被直接回写进持久化设置，把**程序运行时的暂态**与**用户的配置意图**混淆。一旦混淆形成，状态不可逆（每次启动都以污染后的值为基准继续污染）。

## 正解

启动流程遵循 **单向数据流**：
1. **读**：读用户设置的值（用户的输入）
2. **执行**：用读到的值初始化系统状态
3. **更新**：系统运行时的变化（如动态端口偏移、实际运行参数）**只在内存/短期日志中记录**
4. **禁止回写**：**绝对禁止**把执行过程中产生的暂态写回持久化设置

启动成功/失败后，用户设置值保持原样不变，确保：
- 用户在设置页看到的值 = 被系统使用的值
- 重启应用后行为可预测（不会因前次暂态污染而变化）
- 用户可通过修改设置页的值来矫正配置

## 案例

**反例**（proxy-port-no-drift 根因）：
- 用户在设置里设 `port=9890`
- 启动绑定失败 → 尝试 `port+1=9891` → 成功
- **回写进设置** `port=9891`
- 用户重启 → 以 9891 为起点再偏移
- 形成单向漂移、无法回归

**正例**（修复后）：
- 用户设 `port=9890` → 启动直接绑定 9890
- 占用 → 返回错误，**不修改设置**
- 用户看错误信息 → 关占用进程 → 重试
- 设置值始终是 9890

## 适用

- 代理端口 / 绑定地址等启动参数
- 需区分「用户配置」与「运行时实际值」的所有场景
- 跨 Rust 启动层 ↔ 前端设置展示的配置读写
