## PRD 验收标准与约束互容性检查

## PRD 验收标准与约束互容性检查

### 触发场景

task plan 阶段定下验收标准（如「phys_footprint 下降」）和技术约束（如「仅用 mock 平台压测」）时。

### 缺陷：标准与约束架构互斥，直到 check 阶段才暴露

某次量测任务目标是「验证物理内存下降」，压测条件限定「使用 mock 平台验证」。问题：**mock 平台绕开真实转发流水线** (见 [[mock-platform-bypasses-forward-pipeline]])，无法触达真实缓冲/内存累积逻辑；**验收标准（footprint 下降）恰恰依赖这些真实路径才能观测**。结果：验收标准在既定约束下架构上不可达，直到 check 分析数据时才发现"问题"。

### 正解：plan 定版前核对约束与标准互容

### MUST 检查清单

- [ ] **列出验收标准** —— 各个 acceptance criteria（如性能指标、功能验证项、兼容性检查等）
- [ ] **列出技术约束** —— 压测平台选择、测试环境限制、工具/库版本锁定等
- [ ] **逐条核对**
  - 这个标准依赖什么代码路径？（trace source code 需哪些模块工作）
  - 技术约束会跳过这条路径吗？
  - 如有矛盾：要么改标准（可测可交付）、要么改约束（扩大测试范围）
- [ ] **无妥协案例**：若约束无法松动且标准无法替代，需在 plan 阶段明确标注「此标准在既定约束下无法观测」，禁拖到 check 才说"结果达不到"

### 不选别的理由

| 备选 | 否决 |
|---|---|
| 压强行配合（重跑 100 遍看能否触发） | 架构性不可达 ≠ 参数问题，多次重试治标不治本 |
| 扩大样本量（用更大报文） | mock 平台无论报文多大都走短路，增加样本量无效 |
| 期望量测报告说明「无法验证」 | 这是 plan/design 责任，不该变成量测报告的免责声明 |

### 适用

- 任何有明确验收标准 + 受限技术约束的 task
- 特别是性能/行为可观测性与测试工具/环境有强依赖的场景
