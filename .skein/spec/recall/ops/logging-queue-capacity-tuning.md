## 日志队列 capacity 定值方法：从采样均值反推

### 触发场景

应用日志流量稳定后需定值日志队列 capacity（mpsc channel），既要不丢日志（缓冲充足）又要不过度占用内存（常驻预算）。

### 定值方法：单条均值 × 期望并发度

本仓实例：采样真实库 log.db，计算单条日志均值 ≈ 576 KB。期望队列深度设为 512 条（允许短时脉冲），则常驻缓冲上限 ≈ 512 × 576 KB ≈ 295 MB。以此反推 `LOG_QUEUE_CAP`。

```rust
// 采样 log.db，统计日志行大小
// 单条均值：576 KB
// 期望深度（缓冲条数）：512
// → cap = 512

const LOG_QUEUE_CAP: usize = 512;  // 期望 ~295MB 常驻，可根据实际硬件调整
```

### 关键认知：均值与上界的区别

- **均值**：你定的 `cap = 512` 对应的是期望缓冲深度，年长期平均可能只占 80% 空间
- **p99 倍数**：峰值常常是均值的 6+ 倍；单条 576 KB × 6 ≈ 3.5 MB 峰值日志
  - 队列积压时 p99 深度可能达 512 × 6 ÷ 5 ≈ 600+ 条（瞬时）
  - 若硬件仅有 500MB 内存，这个 cap 会撑爆

### 验收

- [ ] 有采样数据证明均值计算（log.db 统计行大小，或代表性样本）
- [ ] capacity = 均值 × 期望并发度（保守估算）
- [ ] 明确标注这个值对应的内存预算（如「≈ 295MB」）
- [ ] 如硬件变化（换库、用户规模 2x），需重采样重算，禁硬编码永远有效

### 不选别的理由

| 备选 | 否决 |
|---|---|
| 用 p99 定 cap | p99 是瞬时峰值，常驻按均值；按 p99 定会过度预分配，浪费内存 |
| 凭直觉设定（如 1000）| 无量化依据，下个季度硬件/用户规模变化就不适配 |
| 无限制（capacity = usize::MAX） | 极端脉冲会导致内存溢出，应用 OOM kill |

### 注意

本方法针对期望缓冲深度定值，非上界保护。若需防止极端溢出，还要配合 try_send 的背压处理（见 [[hot-path-buffers]])。
