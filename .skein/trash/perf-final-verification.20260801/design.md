# 全进程 200MB 总收口验收 — 详细设计

## 为什么需要这个 task

前面 8 个 task 各自有验收，但**都是局部口径**：logs 验 SQL p95、frontend 验 WebKit malloc、window 验合成面、proxy 验 in-flight cap。

「7 个局部达标」推不出「全进程总和 ≤200MB」—— 各 task 的量测在不同时间、不同构建、不同窗口尺寸下做的，数字不可加。且优化之间可能互相抵消（例：bundle 拆分省了 main chunk，但 lazy chunk 常驻反而多）。

本 task 是**唯一的最终判决点**，deps 全部 8 个。

## 量测协议（硬约束，不可协商）

### 判据

| 项 | 工具 | 禁用 |
|---|---|---|
| 内存 | `footprint -p <pid>` 的 `phys_footprint` | `ps rss` / `vmmap` —— 漏算 `Owned physical footprint (unmapped) (graphics)`（[01] 已证） |
| 堆分档 | `heap <pid>` 的 5KB 块数 | — |
| CPU | `sample` / `top -pid` 稳态采样 | 瞬时值 |

`region 数是噪声指标`（[03] 实测同 CSS 下 157/211/218 乱跳），只记字节。

### 场景与稳态

三场景，**各自独立重启进程**，等满 **≥10min** 稳态：

1. 空闲前台（窗口可见，无操作）
2. 空闲隐藏（窗口隐藏，托盘常驻）
3. 50 路并发 mock 流（持续转发峰值，用户定义的峰值口径）

内存曲线有冷（50MB@25s）/ 稳（149MB@22min）两端，**禁同进程内切场景连采** —— [03] 的 release 复验就栽在这（同进程内主进程 116→150MB、GPU 28→64MB，缩窗后反升，两点不在同一稳态）。

### 构建与尺寸

- **release 构建**，`open -a` 启动（非 `yarn tauri dev`）
- 默认窗口尺寸 **1026×759**（`window-default-size` 已删 `maximized: true`）
- 达标口径 = 默认尺寸下的总和；最大化尺寸另采一组作对照，不计入判决

### 压测台

只用 mock 平台与 mock 分组（用户硬约束）。`mock-loadgen-capability` 完成后，mock 已具备：零配额不进 platform 写连接、独立 TTFT / inter-chunk、error_rate 概率注入。

50 路并发的具体流形（chunk 数、间隔、正文长度）在本 task 内定死并写进 spec，保证日后可复现。

## 分解对账表（与 [03] 预算逐项对）

[03] 定的预算：

| 项 | 预算 |
|---|---|
| 主进程 | 30 MB |
| WebKit malloc | 32 MB |
| popover | 22 MB |
| GPU | 18 MB |
| Networking | 6.7 MB |
| 零散 | 20 MB |
| 非合成面小计 | ≤129 MB |
| 合成面 | ≤71 MB |
| **总计** | **≤200 MB** |

本 task 逐项填实测值，**超预算项单列并归因**，不做「总数达标就不看分解」的糊弄。

## 红线回归（四条全覆盖）

| 红线 | 判据 | 怎么测 |
|---|---|---|
| 1 转发延迟与首 token 时延 | 无退化 | 50 路并发 mock 流下记 TTFT 与总延迟，与优化前基线对比 |
| 2 token 计数与费用精度 | 完全一致 | 同一组 mock 请求改前改后逐条比对 token 数与 `est_cost` |
| 3 用户体验 | 无退化 | 18 个页面逐页人工走查：视觉 / 交互 / 布局截断 |
| 4 冷启动 | 不慢于优化前 | 进程启动 → 首屏可交互耗时，多次取中位 |

红线 3 的走查是**人工**的 —— 前端做了删动画、收 hover、去 backdrop-filter 三项视觉改动（用户已拍板全动），必须逐页确认没有意外破相。

## 未达标时怎么办

**不在本 task 修**。未达标项写清三件事：

1. 差多少（字节）
2. 归因到哪个进程 / 哪类分配
3. 是物理下限还是可优化项

可优化的登记为新 task，物理下限的写进 spec 正面说明。

**CPU 特例**（用户已拍板「继续深挖直到达标」）：若空闲前台 CPU 在前端清理后仍 ≥0.5%，本 task 只负责量准并归因，深挖另开 task —— 归因是深挖的输入，混在一起做会让判决点失焦。

## 为什么不选别的

| 备选 | 否决理由 |
|---|---|
| 挂进 `window-default-size` | 它 deps 只有 frontend，量测时 proxy/tokenizer/logs 可能还没合入，数字不完整 |
| 不设收口，各 task 自证 | 没人回答「200MB 到底达没达」，spec 交付时缺最终判决 |
| 本 task 兼做未达标修复 | 判决与修复混在一起，判决点失焦；且修复范围不可预估，会让本 task 无限膨胀 |
| 用 CI 自动化跑 | 内存稳态需 ≥10min、需 GUI 窗口、需人工走查 —— 自动化投入远大于一次性收口的收益 |

## 数据流

```
确认 8 个前置 task 全部 finish 且合入 master
  → release 构建
  → for 场景 in [空闲前台, 空闲隐藏, 50路并发mock流]:
        干净重启 → 等 ≥10min → footprint 全进程 + heap + sample CPU
  → 填分解对账表，逐项对 [03] 预算
  → 红线 1-4 逐条回归
  → 出最终 spec：达标判决 / 未达标归因 / 窗口物理事实
  → 未达标项登记新 task
  → 清理临时脚本与原始采样
```

## 可能性分支（不进当前方案，仅留痕）

- **长跑稳定性验收（24h 内存曲线）** — 触发条件：若 10min 稳态达标但怀疑有慢速泄漏。本批已排除泄漏（[08] 的 `leaks` 仅 5.7MB 全是 macOS CryptKit），当前不做。
- **多窗口尺寸的完整曲线复采** — 触发条件：若 `window-default-size` 的曲线在其他 task 合入后明显失真。
- **CPU 火焰图深挖** — 触发条件：用户已拍板「CPU 继续深挖直到达标」，若本 task 归因指向具体热点则另开 task 承接。
