# s3 预算表逐项对账（对 [03] target-feasibility-ruling 的内存预算分配表）

Parent: [深度性能优化：全进程峰值内存 ≤200MB + 三场景 CPU 下降](map.md)
输入：`s2-measure-3scenes.md` + `assets/results/footprint-s2-*` 原始采样（commit `ca05d8e5` / `bddb4282`），本票**未跑任何新量测**。

## 口径声明

- 数据源 = s2 实测（`.scratch/perf-200mb/s2-measure-3scenes.md`），三场景均：release 构建（`AiDog.app` mtime `Aug 1 14:21`）、独立重启、ISO_HOME 隔离、稳态 ≥600s、`feature/next` 分支。
- 内存判据 = `footprint -p <pid>` 的 `phys_footprint`；「graphics」判据 = 该 pid footprint 输出里带 `(graphics)` 后缀的行之和（`Owned physical footprint (unmapped) (graphics)` + `untagged (VM_ALLOCATE) (graphics)` + `IOAccelerator (graphics)`），其余行归「非合成面」。
- 窗口尺寸：场景1/2/3 均为默认尺寸 `1026×759`（见 `s2-measure-3scenes.md` 最大化对照组段的显式对比基准）；最大化对照组为 `2304×1265`，单独列出不进入默认口径判决。
- [03] 预算表的「WebContent#1 WebKit malloc」「GPU malloc + IOAccelerator」等行名是历史测量下的近似称呼，经反算验证其**真实含义是「该进程 phys_footprint 减/含 graphics 部分后」的整进程占位**（见下方「行含义还原」），本票按这个还原口径对账，否则数字对不上 [03] 自己的合计验证（176.7 = 44+49+22+22+6.7+33）。

## 行含义还原（对账前必须先做，否则误判）

[03] 表格「非合成面小计 176.7」= 44(主进程)+49(WebContent#1)+22(WebContent#2)+22(GPU)+6.7(Net)+33(其余)，逐项相加精确等于小计，说明 **每一行都是该进程/该项的「非 graphics 部分」整值**，不是单一 malloc 子类目。本票据此对 s2 每个 pid 的 footprint 输出做同口径拆分（graphics 行求和 vs 其余行求和），而非只摘 "WebKit malloc" 一行。

## 超预算项逐条归因

### 1. aidog 主进程(Rust)：42–50MB vs 30MB 上限，超 12–20MB

- 数据：三场景 footprint 明细里 `SQLite page cache` 均为 **0 B**（`footprint-s2-scenario1-fg-61827-aidog(main).txt` 等），证实 [08] 票的 `READ_CACHE_DEFAULT_KB=64` 修复已在此构建生效，SQLite 不再是超支来源。
- 剩余主要类目是 `MALLOC_SMALL`：S1 idle 23MB → S3 负载 30MB（仅 +7MB）。tokenizer 四单例（[04]，状态仍 `open`，未处置）理论常驻上限 19+6.7=25.7MB（`GLM4_JSON`+`QWEN2_JSON`，尚不含解析后结构与两个 tiktoken 单例），若真触发理应看到主进程 idle→load 有更大跳变，但实测只 +7MB —— **推测 mock 协议路径未触发本地 tokenizer（可能走上游 usage 或未命中对应协议分支）**，未做进一步验证（不在本票范围，标记需 [04] 补证）。
- **分类：malloc heap（Rust 运行时基线堆），非合成面**。
- **物理下限 vs 可优化：未定论**。关键点——即便 [04] 落地「tokenizer 按需释放」方案，idle 态 23MB 的 `MALLOC_SMALL` 基线本身已吃掉 30MB 预算的 77%，说明 30MB 上限对当前 Rust 运行时基线本就余量很紧，[04] 后续方案选型需要重新核算这个更紧的余量（这是本票发现的新信息，不是重复 [04] 已知内容）。

### 2. WebContent#1 非graphics部分：29→37MB（S1→S3），超预算 +4.9MB

- 数据：`WebKit malloc` 20MB(S1)→19MB(S2)→25MB(S3)，`MALLOC_SMALL` 4.3MB→4.4MB→5.3MB，增量集中在负载态（S3），idle 两场景(S1/S2)稳定在 29MB 左右、不超预算。
- **分类：malloc heap（渲染进程侧的流式转发缓冲），非合成面**。
- **物理下限 vs 可优化：未验证**。[05]（per-connection-cost，状态 `open`）本应拆解 50 路并发下每连接的内存构成，尚未产出结论，本票不越权重复验证，只确认「超支只在负载态出现、且集中在 WebKit malloc 类目」这一事实指向 [05] 的调查范围。

### 3. GPU 进程：S2(隐藏) 37.9MB vs 18MB 上限（非合成面口径），超 +19.9MB —— 本项是「反直觉观察」的直接成因

- 数据对比（`footprint-s2-scenario1-fg-61841-GPU.txt` vs `footprint-s2-scenario2-hidden-72413-GPU.txt`）：
  - `CoreAnimation`：S1 **不存在此类目**，S2 新增 **23MB (Dirty)**。
  - `IOSurface`（Reclaimable）：S1 18MB → S2 **42MB**（+24MB）。
  - `MALLOC_SMALL`：S1 5.4MB → S2 8.7MB，涨幅远小于上述两项，排除「通用堆增长」假说。
- 同步看 WebContent#1：graphics 类目 S1 26MB → S2 55.1MB（+29.1MB），方向与 GPU 完全一致。
- **分类：graphics/合成缓冲，非 malloc heap**。
- **物理下限 vs 可优化：未验证，推测为 WKWebView/CoreAnimation 在窗口被隐藏后保留的合成快照/离屏缓冲（用于快速恢复显示的平台行为），而非代码泄漏或本仓 CSS 问题**——依据是新增内存精确集中在 `CoreAnimation`/`IOSurface`/`Owned physical footprint (unmapped) (graphics)` 三个图形专属类目，跨 GPU 与 WebContent 两个进程同步出现，而两进程的通用 `MALLOC_*` 类目基本持平。**排查到此为止，未做**：Instruments Core Animation profiler 抓栈确认触发点、多次隐藏/显示循环测试是否累积、更长隐藏时长是否继续增长——这三项留给后续票，本票不代为下结论。

### 4. Networking：S3 9.5MB vs 6.7MB 上限，超 +2.8MB

- S1/S2 均落在预算内（6.7/6.5MB），仅 S3（50 路并发流式连接）超支。
- **分类：网络连接的物理成本（每连接 socket/TLS 会话缓冲），非 malloc heap 异常、非 graphics**。
- **物理下限 vs 可优化：部分物理下限**——50 路并发连接本身需要一定的 socket buffer，量级（+2.8MB / 50 连接 ≈ 56KB/连接）不算离谱；是否可通过收缩 `reqwest` 连接池或调小 buffer 进一步压缩，[05]（per-connection-cost，`open`）尚未给出结论，本票不越权判定。

## 反直觉观察归因（S2 空闲隐藏 196.5MB > S1 空闲前台 136.7MB）

**已归因（非「未能归因」）**：差额主要来自 GPU 进程的 `CoreAnimation`(+23MB) + `IOSurface`(+24MB reclaimable) 两个图形专属类目，与 WebContent#1 的 `graphics` 类目同步暴涨（26→55MB）——见上方「归因 3」。三处数字变化方向一致、集中在图形合成子系统而非通用堆，指向同一个现象：**窗口隐藏后 WebKit 的合成快照/离屏缓冲未被释放**，而非预期中「隐藏应释放渲染资源」。

**排查到的深度边界（未继续验证的部分，如实标注）**：
- 未用 Core Animation / GPU profiler 抓具体触发栈，只能确认「类目层面」而非「代码路径层面」的归因。
- 未做「隐藏时长越长是否持续增长」「多次隐藏/显示循环是否累积」的对照实验（team-lead 消息里提到的「10min 稳态爬升」猜测未被证实也未被证伪，本票没有新证据支持或反驳它——只能确认差额落在图形类目，无法判断是否与稳态时长本身相关）。
- 与 s1-preflight 冒烟结论（隐藏 157.7 < 前台 162.8，方向相反）的矛盾**未解释**——两次测量的窗口尺寸/构建版本/稳态时长是否严格一致未核实，本票不具备核实条件（s1-preflight 原始文件未在 `assets/results/` 下留档比对）。

这条结论到此为止，更深的根因定位（代码路径级）超出本票范围。

## 与历史基线（07-29，378.7MB）的可比性核对

`window-size-memory-relation.md` 记录 07-29 在**同一默认窗口尺寸 1026×759、release 构建、纯背景态、≥600s 稳态**下测得 TOTAL **378.7MB**——采样协议（`window-size-measure-protocol.md`）与本票复用的 s2 协议**同源**（s2 即沿用此协议的背景态/稳态硬约束）。

对比对象选 **S2（空闲隐藏 = 背景态）196.5MB**，因为口径维度（前台/背景）与 07-29 一致，S1（前台）不可比。

**核对结论：同口径可比。** 差异：
- 窗口尺寸：均 1026×759 ✓
- 状态：均背景态 ✓
- 稳态时长：均 ≥600s ✓（07-29 走同一协议的 ≥10min 硬约束）
- 构建版本：**不同**——07-29 早于 map 记录的「8 个优化 task」完成之前，s2 是这 8 个 task 全部落地后的构建。这是**预期中的时间序列前后对比**，不是同口径下的重复测量。

**因此这 182.2MB 的降幅（378.7→196.5，−48.1%）可以作为「8 个优化 task 的合计效果」引用，但不能反推「哪个 task 贡献了多少」**——没有中间态数据，无法拆分到单个 task。仅供整体进度参考，不构成本票的判决依据（判决见下）。

## 内存达标判决

**判决：PASS。**

**判据口径：以 S3（50 路并发负载态，默认窗口尺寸 1026×759）为准绳**——因为 [03] 对 200MB 目标的原始定义逐字是「全进程总和在**持续转发峰值（约 50 路并发）**下 ≤200MB」，S3 是唯一在字面上对应该定义的场景。

**数字：TOTAL 184.5MB ≤ 200MB，富余 15.5MB（7.75%）。**

**必须一并声明的限定条件（否则判决会被误读为"全面达标"）**：
1. **此 PASS 仅在默认窗口尺寸 1026×759 下成立**。最大化窗口（2304×1265）TOTAL 296.7MB，超预算 96.7MB——这是 [03] 已经拍板接受的物理代价（合成面∝窗口面积，用户手动放大窗口必然超预算），不是本票需要重新判定的问题，但判决必须声明前提。
2. **S2（空闲隐藏）同样 ≤200MB，但富余只有 3.5MB（1.75%）**——比 S3 薄得多，且这份富余里包含一个未验证归因深度的 GPU 图形合成异常（见上）。若该异常在其他运行环境/更长隐藏时长下更严重，S2 有击穿 200MB 的风险。这不改变以 S3 为准的判决，但作为风险明确记录。
3. 逐项预算表层面**不是全部达标**——非合成面小计 135.65 超出 129 上限 6.65MB，只是因为合成面（48.9MB）比 71MB 预算低了 22.1MB，靠这部分富余抵消，总账才能 PASS。**这是"拆东墙补西墙"式的达标，不是每项都卡进预算**，后续若合成面因其他改动（如流光边框改造引入新合成层）占用回升，总账可能重新击穿 200MB。

## CPU（补充，[03] 有独立目标）

- 空闲前台 CPU < 0.5% 目标：S1 实测 **0.0%**，达标，大幅富余。
- [03] 未对负载态 CPU 给出量化上限（只定性要求"三场景 CPU 下降"），S3 实测 76.0% 无法据此单独判定 PASS/FAIL——**非本票可判定项**，如实陈述实测值。
