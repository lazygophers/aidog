# 03 200MB 目标可达性裁定

Type: grilling
Status: resolved
Blocked by: 01, 02
Parent: [深度性能优化：全进程峰值内存 ≤200MB + 三场景 CPU 下降](../map.md)

## Question

拿 [01] 的实测分解与 [02] 的 WebView 下限，裁定「全进程总和 ≤200MB @ 50 路并发峰值」这个目标是否成立。

三种可能的结局，本票必须落其中之一：
- **成立** —— 锁死 200MB，后续票按这个预算分配额度（WebView X MB / tokenizer Y MB / SQLite Z MB / 其余）
- **口径需改** —— 例如改成「Rust 主进程 ≤200MB，全进程另定」，或「空闲 ≤200MB，峰值另定上限」
- **数字需改** —— 200MB 物理不可达，依实测重设一个有依据的目标

如果结论是「当前架构不可达」，则 map 中 **Not yet specified** 的「是否需要架构级手段」graduate 成新票；否则那条 fog 直接划入 out of scope。

这是 HITL 票——预算怎么分、口径怎么让步，是用户的取舍，agent 不得代答。

## 验收

- 一个明确的数字与口径，写进 map 的 Decisions so far
- 若成立：一张内存预算分配表，每项有上限
- 若不成立：新目标 + 为什么原目标不可达的一句话依据（引 [01]/[02] 的具体数字）

## Answer

**结局 = 成立（数字与口径都不改），但附带一个新增的产品级约束：限制窗口尺寸。** 用户拍板。

### 裁定前补做的实验（本票新增证据）

[01]/[02] 只说清「423MB 是合成面」，没说清合成面**由什么驱动**。裁定前必须知道它是软件浪费（可优化）还是物理成本（只能换取舍）。做了两组实验，都在 `yarn tauri dev` 同一构建下、每轮重启 app + 等 3 分钟稳态后用 `measure.sh mem` 采（同进程内改 CSS 的 A/B 不可靠 —— 首轮就因 GPU 进程未吃满而作废）。

**实验一：假说「`::after` 常驻带 mask 强制提层」—— 证伪。**

假说：`globals.css:843-865` 的 `.glass::after / .glass-surface::after` 即便 `opacity: 0` 也常驻，其 `mask-composite` 强制每个 `.glass-surface`（全仓 116 处用法）提合成层，116 × 2 ≈ 232 ≈ 实测 227 region。若成立，把 `mask` + `conic-gradient` 挪进 `:hover` 分支即可砍掉绝大部分层，且视觉零变化。

结果：

| | WebContent graphics | region 数 |
|---|---|---|
| A 原 CSS | 231 MB | 157 |
| B mask/gradient 挪进 hover | 230 MB | 218 |

**字节数几乎相同，改动无效。** 且 region 数在同一 CSS 下三次采样分别为 157 / 211 / 218 —— **region 数是噪声指标，只有 graphics 字节数可靠**。[01]/[02] 里「227 个 region」的说法不该再作为归因依据。CSS 已 `git checkout` 还原，未留改动。

**实验二：假说「合成面 ∝ 窗口面积」—— 证实，这是决定性证据。**

同一进程、同一 CSS，仅用 `osascript` 改窗口尺寸：

| 窗口 | graphics | WebContent | 全进程 TOTAL |
|---|---|---|---|
| 2304×1265 | **231 MB** | 354 | 505 |
| 800×600 | **52 MB** | 175 | **314** |

面积比 6.07×，graphics 比 4.44× —— 近似线性带常数项。线性拟合两点：

```
graphics(MB) ≈ 7.35e-5 × 面积(px) + 16.7
```

**结论：合成面是窗口面积的物理函数，不是可优化的软件浪费。** 仅缩窗一项就省 191MB，与 [01] 的两个旁证自洽（缩窗 GPU CPU 36.9%→16.6%；隐藏窗口降 212MB）。**推论：任何「优化代码把 441MB 压下去」的方案都不成立，只能换窗口尺寸。**

### 裁定

目标**维持不变**：全进程总和 ≤ **200MB** @ 50 路并发峰值。

依据 —— 峰值口径几乎等于空闲口径（[01] 实测 619.8 vs 617.7），50 路并发只让 Rust 主进程 +7MB。**所以这个目标实质是在约束空闲态，转发负载不构成压力。**

代价 —— 非合成面（176.7MB）已吃掉 200 预算的 88%，**光把窗口缩到 0 也差 23MB 才够**。因此必须两头一起压：

### 内存预算分配表（全进程 ≤200MB）

| 项 | 现状 (release 空闲) | **上限** | 手段 / 归属票 |
|---|---|---|---|
| aidog 主进程 (Rust) | 44 | **30** | tokenizer 按需加载 + 用完释放（红线 2 禁降精度）→ [04]；SQLite page_cache / mmap 调参 |
| WebContent #1 WebKit malloc | 49 | **32** | bundle 拆分、减常驻 JS heap → 新票 |
| WebContent #2 (popover) | 22 | **22** | **不可省** —— [02] 已证关窗也不还内存（tauri #5397），合并进主窗口只值 22MB 不划算 |
| GPU malloc + IOAccelerator | 22 | **18** | 随合成层数下降，无独立手段 |
| Networking | 6.7 | **6.7** | 不可动 |
| 其余零散 | 33 | **20** | — |
| **非合成面小计** | **176.7** | **≤129** | |
| **合成面（窗口 surface）** | **441** | **≤71** | **只能靠窗口尺寸约束** |
| **合计** | **617.7** | **≤200** | |

**由预算表反推的窗口约束**：71MB 代入拟合式 → 面积 ≈ 740000 px → **约 1150×750**。

这是**新增的产品级硬约束**，此前不在图上：默认窗口尺寸与最大可用尺寸需要限制在此量级。用户已知悉此代价并选择接受（明确否掉了「改口径只管非合成面」与「改数字到 350MB」两个替代方案）。

**留给实施票的责任**：这条约束怎么落地（限制 `tauri.conf.json` 的 `maxWidth/maxHeight`？还是不限制窗口但接受大窗时超预算、只承诺默认尺寸下达标？）本票不定，交给后续 spec —— 但「用户手动拉大窗口就会超 200MB」是物理事实，不可能通过代码规避，spec 必须正面写明这一点。

### CPU 目标（用户拍板）

**空闲前台 CPU < 0.5%。**

参照系：[01] 实测窗口隐藏时全进程 0.2%，说明 UI 静止态本该接近零。当前 50.2%。

这要求**彻底消灭**两件事，而非降频：
1. 软件光栅化路径（GPU 进程 54% 采样在 `CA::CG::DrawConicGradient::draw_color`）
2. 逐帧全量 style 重算（`Document::resolveStyle` → `TreeResolver::resolvePseudoElement`，由 `@property` 注册属性被动画驱动）

**推论：任何「常驻动画」都不能留** —— 包括 `body::before` 的 `bgShimmer 32s`（当前在本机因 `reduceMotion=1` 未跑，但默认用户会跑），以及散落的 13 处 `animation:`。这条推论超出流光边框一处，需在 spec 里逐个清点。

### 流光边框处置（用户拍板）

**改实现，视觉保留。**

不再用 `@property --flow-ang` + `@keyframes` 动画角度（那强制每帧全量 style 重算，根本无法 compositor-only），改为**把一个静态 conic 渐变层用 `transform: rotate()` 转起来** —— `transform` 走合成器，渐变只光栅化一次。

**待验证的风险（留给实施票，不在本票裁定）**：当前效果依赖 `mask-composite: exclude` 做 1px 边环镂空。`transform` 旋转的是带 mask 的层，旋转时 mask 与元素圆角的对齐关系会变（`border-radius: inherit` + `inset: 0` 的方形层旋转后不再贴合）。可能需要改成「外层固定 mask + 内层旋转渐变」的两层结构。实施前必须先做视觉比对，红线 3 要求视觉不降级。
