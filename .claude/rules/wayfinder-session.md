# wayfinder 调研轮：票面预设、agent 派发、ask-ui 解读

适用于「ask-ui 定向 → 建票 → 派后台 agent 取证 → 结票」的调研型 session。

## 1. 票面预设事实必须标「未证实」

预设来自主会话记忆，下游若不先结取证票就会把错前提当靶子。

1. **Question 里凡来自记忆、未带出处的外部事实，显式标注「未证实，先核对」**，并要求 agent 报告逐条判定票面预设真假（推翻也算结票产出，不是失败）。
2. 依赖这些事实的下游票必须 `Blocked by` 取证票。

## 2. 状态迁移指令要贴进派发 prompt

tracker 约定值是 `claimed` / `resolved`（`docs/agents/issue-tracker.md` Wayfinding operations 节），agent 不会自己去读那份 doc——不贴进 prompt 就会写成 `done` 等近义词。派发 prompt 原样贴三行：开工置 `Status: claimed`；结票在文末追加 `## Answer` 段并置 `Status: resolved`；**状态词只有这两个**，禁 `done` / `closed` 等近义词。主会话收报告后仍 grep 一次 `Status:` 核对。词表贴进 prompt 仍不够：每张票合并后当场 grep `Status:` 与 `## Answer`，不留到 feature 收尾。

## 3. ask-ui 选项题收到「只写补充说明、未选任何选项」

此时**语义是主会话解读出来的**，不是用户拍的板。

1. 解读写进 map 的 Notes / 决策历史，标明「用户未选项、系解读」，「我说」字段照抄用户原话，不誊写解读后版本。
2. 解读承担方向性权重（定对象、定终点这类）时，下一轮 ask-ui 顺带一题复核「我理解你是 X，对吗」，不把解读当拍板。
3. 镜像情形：**custom 被选中但 supplementaryText 为空**——语义只有「用户要自定义」没有值，同样是解读。方向性权重时下一轮表单把该题重发补值（custom 已点可作默认态）。
4. 变体：`w_unknown`、`w_paths` 未选项只写补充，`w_reject` 选 503 但补充写「400 或者是别的 4xx」（选项与补充冲突）。冲突时**补充文本优先**（更具体），仍记「系解读」，下一张表单原样复核。
5. 变体：未选项、补充给出可执行值（「6 个变体」）。**补充文本含可执行值时直接按值执行**（记「系解读」+ 账本「我说」抄原话），不等下一轮拍板；执行不了的残余歧义（本例「变体」没说变布局还是视觉维度）并入下一张表单复核。「系解读」只降记账等级，不降执行等级——空等一轮追问是浪费。

## 4. 插话方案与正式拍板冲突

用户在对话里插话提出方案、后续正式拍板选了别的（可能互斥）方案时，按下述流程化：

1. 插话方案是**候选**，不是拍板。下一轮 ask-ui 原样摆成选项，不因「与当前倾向矛盾」剔除。
2. 正式拍板否掉它 → map 的 **Out of scope** 记一行：方案 + 否掉原因 + 复活条件（「仅当 X 才重开评估」）。
3. 后续兜底链不静默复活：回落路径显式写「回落 X，不回 Y」（例：回落端口方案，不回 path 方案）。
4. 账本「我说」照抄插话原话，不誊写成拍板版本。

## 5. 覆盖 session 边界（用户明示或 agent 自行连做）

「停在 research」「一 session 一票」是防上下文腐化的默认，两种情况可覆盖：**用户当轮明示**，或 **agent 自行连做且下一票无新决策、上下文余量足**（例：前票拍板后连做后一张纯汇编票）。覆盖时：

1. 账本记决策行，「我说」抄原话（用户明示时）；自行连写照「无，自行判断」+ 判断依据。
2. map 的 **Notes** 补一行覆盖事实——漏记时其他会话读 map 会误判成违规（只写进账本 / `.scratch/<spec>/memory.md` 不算记）。两处都记，不是二选一。
3. 连做后续票时每票收尾照常走 wayfinder 第 5 步（毕业 fog、追加 Decisions so far、刷新 frontier），不省略 map 维护。

## 6. 多张 grilling 票合并成一张 ask-ui 表单

多张票可合进一张表单，外加一题复核，一轮问完。两个条件同时满足才可合并：

1. **票之间互不当输入**：B 票的选项不取决于 A 票的答案。有依赖就用 ask-ui 分支题或拆两轮，不把「假设 A 选了 X」写进 B 的选项。
2. **每题标明所属票号**（标题前缀 `[04]` 之类），结票按票号把答案写回各自 `## Answer`，不合写。

上一轮留下的复核题顺带塞进同一张表单，不单独开一轮。

## 7. 收到新答案先对照已定决策查冲突

每张票收到答案、结票之前，逐条对照 map 的 **Decisions so far** 和当天账本，检查新答案会不会让已定决策在某条代码路径上失效（短路、兜底、bypass 最易漏）。例：新答案「过滤并入 filter_candidates」会被单平台分组短路绕过（`candidates.rs:104`），与已定决策「分组没有决策平台就报错」冲突。有冲突时：① **不自己挑边**，下一张表单把冲突原样摆出（「A 与 B 在 X 路径上冲突，选哪个」），附冲突点 file:line；② 账本记「改成 / 原本」两边，「原本」写被冲突的决策。

## 8. 选项里引用代码先例之前先核实

选项或 background 里的先例若不实，用户可能已按错的先例做了选择。例：表单写「embeddings 按路径识别」作先例，实际能识别但转发报 400。

1. 选项或 background 写「现有 X 就是这么做的」必须带 file:line，且这一轮真读过那段代码（识别到了 ≠ 能跑通，要看到端到端结果）。查不到标 `推测:`，或先派 Explore 查清再发表单。
2. 已发出的先例错了：当场更正，并检查依赖该先例的答案，受影响的放进下一张表单复核（按 §3 处理），不默认用户答案不变。

## 9. 等 ask-ui 提交：用分离后台任务跑

1. 用户要慢慢拍板的表单，`ask-ui ask` 用 `run_in_background` 跑：分离运行、跨轮存活、退出时 harness 自动通知；超时上限 600000（10 分钟）只约束前台命令。后台任务撞 30 分钟上限被杀时靠 `ask-ui resume` 接回。
2. 任务被杀不等于表单没了：`ask-ui resume` 接回同一张表单，别重发。
3. 禁写 `sleep` 循环等提交（也会被权限拒）。

## 10. 派 research agent 的落盘指令要带回退口径

research agent 可能只有 web 读取类工具（无 Bash/Edit/Write），「把报告写到 .scratch/<spec>/research/」根本执行不了。

- 派发前无法预知工具集时，落盘指令写成双口径：「若无文件写入工具，报告全文直接回传，由主会话核对后落盘」（同模式先例：本文件 §2、parallel-implement.md §2）。
- 回传报告落盘时文件头注明取证方式（如「agent 无本地文件工具，报告经主会话对照官方页面核对后写入」），别让后人以为出自一手文件操作。

## 11. 报错语义 spec 要对照现有短路路径

需求带「必须报错 / 不得静默回落」语义时，既有短路/bypass 会静默绕过新链路：「单平台组 bypass」在多平台组只剩 1 个 Enabled 平台时同样命中（等效单平台组），「声明平台全禁用 → 503」会被静默打到唯一 Enabled 平台。guard（例 `direct_ids 非空 && len > 1`）要显式放到短路之前。

1. spec 定「报错/阻断」语义时，逐条列出会静默绕过它的既有短路路径（单平台 bypass、status bypass、passthrough 豁免这类），写明新 guard 相对短路的位置——票面不写位置，agent 按最小改动默认放短路之后。
2. 测试必含「等效退化形态」各一例：多平台组退化到只剩 1 个可用平台，与字面单平台组（len==1）分开验证。
3. 「字面 X vs 等效 X」的语义差异在 spec / 表单显式拍板，不留 agent 推断。

## 12. 行为改造的拍板点先从现状审计导出

需求原话拆不出真正的拍板点——取舍点要对照现状链路导出，才能问在要害上。

1. 行为改造类需求（排序、优先级、过滤这类「现状已有一条链」的），先审计现状链路全貌（主键/次键/兜底/短路各是什么），再逐条对照导出拍板点发问。
2. 依据：先画现状排序链路才问得出真取舍（例：coding plan 优先是否压过 level_priority、适用模式、「便宜」口径、余额维度口径；审计发现 coding plan 现状是「模式排序后的二值上浮」，不审计问不出「是否压过 level_priority」），拍板项与现状脱节时答了也落不了地。
3. 反例：按需求原话直接拆——「优先使用 coding plan 的」照字面一项，漏掉它与既有主键的相对位置这一真正要拍的事；agent 只能自行假设，合并时对不上。
4. 与 §8 分工：§8 管「选项里引用现状先例要真读过」；本条管「拍板点清单本身从现状审计导出」，先审计、后发问，顺序不可换。

## 13. 拍板任务执行不能：事实唯一时不回落表单

例：表单拍板「补齐 27 平台 logo_url」，双源验证发现这些品牌在 simpleicons 全不存在（官方全量清单正则零命中 + 候选 slug 全 404）——拍板前提（「有 slug 可补」）被外部事实否定，「补齐」物理执行不能。

- 前提被事实否定、且**没有候选方案**（母公司 logo 顶替属错误品牌映射）时，不回落表单重问：按事实唯一收口，账本记「执行不能」条目（「我说」照抄表单拍板原话，「为什么」带双源出处），审计报告单列一行告知。判据：事实只有一个答案，不存在拍板空间，重问浪费一轮。
- 有候选方案（A/B 取舍、改口径重做）才回落表单——那是拍板空间，不是执行不能。

## 14. 调研报告的存在性判断必须 grep 代码

对比调研报告称「aidog 缺 Gemini 协议」，实现票开工审计发现 Protocol 枚举、converter、registry 条目全在——报告取协议清单来自 CLAUDE.md 文档的协议列表，「文档清单里没有」不等于「代码里没有」。

- 「项目缺 / 没有功能 X」的存在性判断，真值源是代码与 registry 数据（grep 枚举 / converter / `src-tauri/defaults/registry/`），不是任何文档（含 CLAUDE.md / GLOSSARY.md）——文档滞后于代码是常态。
- 与 §8 分工：§8 管「选项里引用先例要真读过那段代码」；本条管「调研报告对功能有无下结论前要 grep 过代码再写」。
- 被误判的功能进实现段时，实现票开工先审计存在性再动手（零改动结票是正确收口，不是浪费：误判在调研段拦下比在代码里撞上便宜）。

## 15. 表单前提里的「做不到 / 写不出」也要先 grep 现有能力

§14 的存在性判断同样覆盖「X 做不到 / 写不出 / 要新造」：发表单前 grep 一遍涉及的能力，命中现有实现就写进 background，不把「要新造」当前提（例：表单前提写「检测器正则写不出来」，实际中间件早有 regex + validator 内置识别器，`aidog_db/src/schema.rs`、`aidog_middleware/src/validators.rs`）；前提来自记忆而没 grep 过，按 §1 标「未证实」。

## 16. 口径统一类拍板必带「存量怎么办」子题

拍板统一换算 / 计量口径（例：K/M 窗口基数 1000 vs 1024）时，表单只问新值口径没问存量——库里 1024 基与新落的 1000 基并存，事后只能留遗留，下次改口径还得重新对齐。凡「统一口径 / 改基数 / 改单位」类拍板，选项或子题必须显式覆盖存量处置：一并改写（= 重核验全量存量）、保持不动两套并存、或只管新值，三选一让用户拍，不留 agent 推断（§12 在口径类题目上的具体形态）。

## 17. 跨票移交必须在接收票票面登记

例：票 A 把「费用状态 UI 展示」推给票 B，票 B 票面没有这项、验收也没声明遗漏，直到用户问起才发现——移交项在两票间静默蒸发。

- 票 A 把工作推给票 B 时，同轮把移交项写进票 B 票面（一行：做什么 + 被 A 票移交）；只写在票 A 的 Answer 里不算登记。
- 票 A 结票 Answer 单列「移交项 → 接收票」清单；主会话合并票 A 时 grep 接收票票面核对已登记，未登记即补登记或改记当日账本遗留。
- 接收票结票时逐项核移交项已做或显式声明遗漏，不默认「上游写了就有人接」。
